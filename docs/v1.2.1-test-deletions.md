# v1.2.1 — test deletions and weakenings ledger

Release criteria §5.3 and §5.4. A row is required for every test **removed** and
every assertion **weakened** in `tests/test_wave1_*.py` or `tests/wave1-*.test.ts`
— and, by the same logic, anywhere else a phase changes what a test pins.

A count-only ledger is satisfied by neutering a test in place, which is precisely
what `integrity.py:404`'s `return True` already is. So the trigger is not deletion.

**Classification is mechanical, not editorial.** A row may be filed *modified*
only if its diff touches no assertion line:

```
git diff <phase-base> -- <file> \
  | grep -E '^[-+].*(expect\(|assert|toBe|toThrow|pytest\.raises)'
```

Empty → legitimately *modified*. Non-empty → it is a *weakened* or *corrected*
row and carries the fuller justification below.

## Phase 1 / 3 — a removed guard

`hooks/stop.mjs` drift-guard **check (c)** is removed, deliberately, under §1.2 and
Risk 4 ("where a phase deletes a call site, delete its test deliberately and record
why"). It pushed `tick N appears mid-flight` when `current_step < 9` and the run was
live — the same condition Guard 3's continuation check owns, evaluated one guard
earlier, with a message that named the problem but not the remedy.

No coverage is lost: the condition still blocks (exit 2), now via the guard that
tells the agent to call `TaskOutput` with `block:true` or `Monitor` the artifact it
owes. `mcp/tests/stop-incomplete-tick.test.ts` covers it end to end and is green.

`hooks/stop.mjs`'s drift guard is also now **scoped to the orchestrator**. It never
was, and only looked scoped because its gates were inert; a sub-agent ending its own
turn was being asked to produce the artifacts it had been spawned to produce.
`stop-incomplete-tick.test.ts`'s "the guard is scoped to the orchestrator" cases had
asserted this all along and were passing for the wrong reason.

Phase 8 measures the roles, so before spending on the matrix each spec was
checked for the defect the pilot found in `evals/tick`: a case grading a
distinction the agent file never draws. Three axes, three defects, one row here.

| file | test | class | phase base | justification |
|---|---|---|---|---|
| `mcp/tests/agent-eval.test.ts` | `set-level cases > scores h003-family-collision correct when ANY review is rejected on h003` | **corrected** | `aa44ac4` (8.x) | The assertion pinned the weakness as the specification. `h003-family-collision` holds three proposals sharing `approach_family=algo`; H003 permits one, so two must be rejected. Scoring on *any* rejection meant a verdict that rejects one and approves the other two — leaving a colliding pair standing, H003 still broken — scored `correct`. That is the exact verdict the case exists to catch. `expect_note` justified identity-freedom ("which member is rejected is a judgement call"), which is true, and silently extended it to count-freedom, which is not: *how many* is arithmetic on the payload. **Net strengthened:** the row now pins `incorrect` for the one-rejection verdict *and* two new cases were added beside it — a resolved-collision verdict scoring `correct`, and a derivation test computing each floor from its own payload (`Σ max(0, groupsize − 1)` for h003, `Σ max(0, shared − floor(N/2))` for h004) so a hand-typed floor cannot drift from the case it describes. `ci/agent-eval.mjs` gained `expect_min_rejections`, defaulting to 1 — every other set-level case keeps its current meaning. |

Two further corrections in the same pass changed **expectations, not tests**, so
they carry no ledger row under §5.4 (the assertion-line diff is in spec data,
not test code) — recorded here because they have the same shape:

- `evals/mutagen/spec.json`, case `dream-k-small-tick` — the case that exists to
  grade the `dream_k` gate asserted `proposals.min: 4`, applying `train_k * 2`
  and dropping the floor. `agents/evor-mutagen.md` computes
  `min(max(strategy.dream_k or 0, train_k * 2, 5), 7)`, so with `train_k=2` the
  answer is 5 — and 4 is the one count the formula can never return. A lenient
  expectation cannot fail, so the oracle and degenerate-floor checks in
  `eval-specs.test.ts` both passed it; it would have been reported as the
  dream_k gate holding. Now `min: 5`, and `eval-specs.test.ts` recomputes the
  formula for every case that grades a count, plus asserts the formula string is
  still the one the agent file states.
- `agents/evor-forge-analyst.md` — `verdict="rejected"` had two stated
  conditions and `verdict="approved"` had none, while three cases graded
  `approved`. The rejection list was never declared exhaustive, so the model had
  no stated ground for the complement. Pass 5 now states it. This is the tick
  defect exactly, in a second role.

The gate that found the first and third is `ungroundedEnumValues` in
`ci/eval-core.mjs`: for every enum value a spec grades, does the agent file
state *when* it applies? A line naming a value alongside its siblings is a
vocabulary list and defines nothing — counting mentions scores `rejected`
(2 mentions, no rule) as grounded, which is why the check is structural. Its own
gate is the real pre-fix `evor-tick` prose: it must report `scored`, `rejected`
and `skipped` ungrounded and `failed` grounded, which is what the pilot observed
the model do.

### The third instance — `evor-probe`'s `gradient_health`

`agents/evor-probe.md` Check 2 ended `Classify: "healthy", "exploding",
"vanishing", "unstable" (high variance, no clear trend)` — a vocabulary list
with one parenthetical. The thresholds above it (`max(grad_norm) > 100`,
`mean(grad_norm[-10:]) < 0.001`) govern which *signal* to emit, not which value
the field takes, and `"healthy"` was defined nowhere. Three cases graded it.
Same defect as tick and forge-analyst, third instance. Check 2 now derives all
four values from those same thresholds and states that `"healthy"` is the
complement rather than the fallback for an uncomputable series.

`ci/role-eval.mjs` was mid-run against this exact file when the defect was
found, which surfaced a fourth: it read the agent file at startup and re-read it
at write time to compute `agent_sha256`. Over a run measured in hours those are
not necessarily the same bytes, so the report would have attributed its numbers
to a file version that never produced them — the one thing a fingerprint exists
to prevent. It now hashes the bytes it used. The 8.2 run was stopped at 23 of 66
cases ($1.35) and relaunched against the corrected file rather than left to
finish and be fingerprinted wrongly.
